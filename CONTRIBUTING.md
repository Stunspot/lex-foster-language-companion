# Contribute

Thank you for helping make language assistance more useful and less silly.

## Report a problem

Open a GitHub issue and include:

- the product version, host, and relevant package path;
- the language, variety, audience, relationship, and task;
- the exact input, with private details removed;
- the response or behavior that failed;
- the behavior you expected;
- whether the problem affects meaning, register, culture, accessibility, privacy, security, or authority.

Use a synthetic example when the original contains personal, medical, legal, immigration, employment, or confidential information.

## Propose a product change

1. Start from the current `main` branch.
2. Keep the change tied to one observable behavior or customer need.
3. Update the canonical source under `source/` first.
4. Add or revise a behavioral eval when the change protects a transferable judgment.
5. Run the learner-profile tests, release validator, and relevant distribution profile.
6. Update customer documentation when the user journey, package shape, command, boundary, evidence claim, or recovery path changes.
7. Open a pull request with the problem, smallest repair, checks run, and residual uncertainty.

Prompt-bearing changes must preserve Lex as one coherent language educator. Avoid policy-block accretion, questionnaire intake, gamification, fake official assessment, and claims of equal competence across every language.

## Propose a documentation change

Begin from the reader's task, not the source file that happens to contain the information.

1. Identify the reader, use moment, top task, applicable version, and successful outcome.
2. Trace consequential claims to the current package, tests, schemas, accountable product decision, or retained evidence.
3. Choose the right topic type: tutorial, how-to, reference, explanation, troubleshooting, or release communication.
4. Write procedures with a starting state, prerequisites, ordered actions, expected results, branches, safe stopping, recovery, and completion proof.
5. Use meaningful headings and links, exact product terms, logical list and table structure, and nonvisual equivalents.
6. Run the Hesperos accessible-Markdown lint on changed Markdown and inspect semantics manually.
7. Update [Documentation maintenance](release-v0.1.0/docs/MAINTENANCE.md), the source ledger, or release notes when the change affects governance or evidence.

Public artwork is raster-only in this repository workflow. Preserve the approved WebP, PNG, or JPEG source and its existing references. Do not introduce an SVG asset or substitute artwork without explicit owner authorization.

## Translation and community knowledge

A language or cultural correction should name the variety, community, context, and source of authority. Community-provided knowledge remains attributed; one speaker or source does not silently become a universal rule.

## Completion evidence

A documentation contribution is ready for review when:

- the intended reader can find the topic from [DOCUMENTATION.md](DOCUMENTATION.md);
- the task, expected result, failure branch, and next action are clear;
- links and literal paths resolve;
- claims match the evidence state;
- accessibility was reviewed at the available depth;
- untested behavior and owner decisions remain explicit.
